# Hanui 상황별 검증 — 2026-10-10

실제 Gemma 4(`gemma-4-26b-a4b-it`, thinking minimal), 연결된 KMM 고문헌 DB, Chromium의 앱 화면을 사용했다. 환자 데이터는 임시 SQLite에 저장했고 기존 사용자 기록은 변경하지 않았다. 시간은 전송 버튼 클릭부터 화면 응답 처리가 끝날 때까지의 단일 실측이다. 평균이나 보장 시간이 아니다.

12개 대화 상황 중 수정 후 결과를 포함해 11개 통과, 1개 미통과다. 서로 다른 테스트 실행과 수정 전후의 결과를 모은 표이며 최종 코드에서 12개를 연속 재실행한 결과는 아니다. 기록 조회 재검증은 앞서 검증한 산책·커피 발언을 임시 DB에 합성 입력해 문맥을 준비한 뒤 실제 모델을 호출했다.

추가로 실제 추론 도중 취소하면 메시지·작업을 저장하지 않고 요청 잠금을 해제하는 것, 다른 대화의 일정이 변경되지 않는 것, 브라우저 JavaScript 오류가 없는 것을 확인했다. 모바일 메뉴·대화 삭제·초안 보존·모든 메뉴 이동 및 리포트 초안 확인→적용→수동 편집→저장/재조회 화면 테스트도 통과했다. 이 두 화면 테스트의 모델은 고정 응답 대역이며 실제 Gemma 리포트 생성 품질을 검증한 것은 아니다.

## 발견한 오류와 수정

- 과거 기록 조회에서 모델이 이전 환자 발언을 새 관찰로 다시 제출해 검증 오류가 발생했다. 프롬프트 보강만으로 해결되지 않아 `records_read` 역할을 추가했다. 조회 에이전트 출력은 답변만 요청하고 기록·일정 변경 액션을 거부한다. 실제 조회 재검증에서 2잔 답변과 관찰 수 유지가 확인됐다. 기록 작성의 기존 원문·날짜·수치 검증은 유지한다.
- 모바일 메뉴 버튼의 `transition: all`이 숨김 상태 전환에 영향을 주어 메뉴를 열 때 포커스 이동이 실패했다. 해당 버튼의 전환을 배경색·글자색으로 제한했다. 실제 브라우저에서 열기 포커스, Tab 순환, Escape 복귀 테스트가 통과했다.

## 남은 제한

- 메인이 한 턴에 하나의 작업 역할만 선택한다. “원문 검색과 일정 추가” 같은 복합 요청은 일부 작업이 빠질 수 있다. 서로 다른 작업은 별도 메시지로 요청해야 한다.
- 최초 실행의 다섯 번째 질문은 Google API 한도로 실패했다. 해당 요청은 저장되지 않았다. 이후 호출 간격을 늘려 남은 상황을 확인했으며 키를 바꾸어 한도를 우회하지 않았다.
- 이번 검증은 웹검색·실제 병원 예약 확정·앱 종료 중 알림 전달까지 검증하지 않았다. 캘린더 저장은 앱 내부 일정 관리이며 병원 예약 확정과 다르다.
- 응답 속도와 모델의 역할 판단에는 변동이 있다. 이 결과만으로 모든 표현이나 장기 사용의 정확도를 보장하지 않는다.
